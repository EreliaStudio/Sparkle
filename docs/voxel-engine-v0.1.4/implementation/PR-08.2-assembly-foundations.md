# PR 08.2 — Fixed Assembly and Elements

## Scope

Implement only Core definitions for immutable, shareable hierarchical bodies. No model instance, pose, animation, rendering, mesh, geometry view or equipment attachment is part of PR 08.2.

## Vocabulary

- `Element`: concrete extensible body element, possibly without geometry.
- `Assembly::Element::AttachmentPoint`: a named local rigid frame with at most one structural child. The geometric frame can later be reused by instance-level equipment.
- `anchor`: the Element's incoming rigid frame, stored as a matrix.
- `Assembly`: immutable shared owner of the complete tree and lookup table.
- `Assembly::Builder`: single-use publishing mechanism.

The names `Assembly`, `Assembly::Element`, `Assembly::Element::AttachmentPoint` and `anchor` are approved. The anchor remains a rigid local frame (position and orientation) stored as `Matrix4x4`.

## Ownership and construction

The Assembly owns the root `unique_ptr<Element>`. Each Element owns descendants through `Assembly::Element::AttachmentPoint`. All objects are movable during construction; no deep polymorphic copy is supplied. Both moved existing objects and direct in-place construction are supported, preserving concrete derived types.

The root and descendant Elements can be prepared before entering the Builder, or completed through `builder.root()`. `build()` validates unique Element names, builds a `name -> const Element*` index and publishes `shared_ptr<const Assembly::Data>` without copying Elements. The Builder is then consumed. After publication, `Assembly` exposes only const element and attachment-point access, even when the `Assembly` itself is non-const. Previously retained mutable construction references must not be used to mutate published data: this is an explicit developer contract, not a runtime-enforced guarantee.

## Geometry

The anchor and each attachment point hold a `Matrix4x4` that represents only a rigid position/orientation. Callers configure position with `Vector3` and optional orientation with `Quaternion`. Child anchor and parent attachment point frame coincide in the fixed structure.

Future instance transforms and non-inherited per-Element scaling are deliberately excluded.

## Public usage

```cpp
spk::Assembly::Element arm("leftArm");
arm.addAttachmentPoint("wrist");
arm.attach<spk::Assembly::Element>("wrist", "leftHand");

spk::Assembly::Builder builder;
auto &torso = builder.setRoot<spk::Assembly::Element>("torso");
torso.addAttachmentPoint("shoulder", {1, 2, 0});
torso.attach("shoulder", std::move(arm));

spk::Assembly assembly = builder.build();
const spk::Assembly::Element &hand = assembly.element("leftHand");
const spk::Matrix4x4 &shoulder = assembly.attachmentPoint("torso", "shoulder");
```

## Invariants

- AttachmentPoint names are unique within their Element.
- Element names are unique across an Assembly.
- One structural child maximum per AttachmentPoint.
- AttachmentPoint names and geometry remain when a structural child is removed.
- Missing attachment point, occupied attachment point, missing Element, incompatible typed access and duplicate names raise `spk::Exception`.
- A free attachment point's `child()` returns `nullptr`.
- `attachmentPoints()` is a read-only vector view. Adding an attachment point can invalidate existing references unless appropriate capacity was reserved.
- Element has no parent pointer and no InherenceTrait dependency.
